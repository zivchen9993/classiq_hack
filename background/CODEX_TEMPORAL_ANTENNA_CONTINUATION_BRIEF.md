## Formulations to retain and add

### A. Snapshot antenna problem

Retain the existing per-sector one-hot snapshot QUBO as the smallest validation problem:

\[
x_{s,k}=1 \quad\Longleftrightarrow\quad \text{sector }s\text{ uses tilt }k.
\]

The default high-throughput snapshot solution currently increases handover failures substantially. Do not present it as an unqualified network improvement. Either add operational guardrails or present a clearly labelled Pareto frontier.

### B. Existing candidate-chain temporal problem

Retain the current formulation as a **sanity check and negative control**, not as the scalability headline:

\[
J=\sum_t r_t(m_t)+\lambda\sum_t c_t(m_t,m_{t+1}).
\]

Because this is a chain over a small candidate pool, exact dynamic programming solves it in polynomial time. Use DP as the correctness oracle. Explicitly state that this formulation does not offer a credible route to classical outperformance.

### C. Main formulation: direct spatiotemporal antenna optimization

Implement a direct formulation that optimizes every sector and timestep jointly, rather than first reducing every timestep to a small candidate pool:

\[
J(x)=\sum_{t=1}^{H} C_t(x_t)
+\lambda\sum_{t=1}^{H-1}\sum_s \operatorname{switch}(x_{s,t},x_{s,t+1}).
\]

Use one-hot variables `x[t,s,k]`. Each `C_t` is the validated snapshot unary-plus-spatial-pairwise antenna objective at time `t`. Express unequal consecutive tilts quadratically under the one-hot constraint, for example through `1 - sum_k x[t,s,k] x[t+1,s,k]`, with optional distance-weighted switching costs.

This produces a spatiotemporal interaction graph with both spatial and temporal edges. It avoids the artificial candidate-chain shortcut and is the correct main problem for evaluating scalability.

Support, as optional controlled extensions:

- maximum tilt change per update;
- a total reconfiguration budget;
- per-sector switch limits;
- handover, outage or cell-edge SINR guardrails;
- robust cost over several traffic-demand scenarios.

Add only extensions that are encoded correctly and benchmarked. State when slack variables or higher-order reductions are introduced and count their resource cost.

## Port DCQO and BF-DCQO to Classiq

Yes, this is feasible. Implement a real gate-level Classiq version; do not attempt to upload the reduced NumPy tensor evolution as if it were a circuit.

Create a focused module such as `classiq_dcqo.py` with the following structure:

1. Allocate one qubit per one-hot variable.
2. Prepare one W/Dicke-weight-one state for every `(t,s)` one-hot block.
3. Build the diagonal cost Hamiltonian from the exact same QUBO/Ising coefficients used by the other solvers.
4. Build the constraint-preserving XY ring or chain driver within each block.
5. Construct the first-order counterdiabatic operator

   \[
   A^{(1)}(\lambda)=\alpha(\lambda)i[H_d,H_f].
   \]

   Generate and simplify its Pauli terms programmatically from the driver and cost Hamiltonians. For a quadratic diagonal cost and two-qubit XY driver, expect local Pauli strings, including higher-body strings where spatial or temporal couplings touch a driver edge. Merge identical strings and remove negligible coefficients using a documented tolerance.

6. Implement each digitized step using Classiq Hamiltonian/Pauli exponentiation, preferably `suzuki_trotter`, with explicit order and repetition count.
7. Keep the schedule values and `alpha(lambda)` classically calculated and logged. They are not variational QAOA parameters.
8. Implement BF-DCQO as an outer sequence of DCQO executions:
   - sample the current circuit;
   - compute one-hot marginals;
   - update longitudinal bias terms;
   - rebuild or re-execute the next circuit;
   - always score samples using the original unbiased antenna objective.
9. Save the synthesized Classiq program and circuit metrics for each tested instance.

If symbolic execution parameters allow one synthesized program to be reused across schedule or bias values, use them. Otherwise report every resynthesis explicitly as classical overhead.

## What would count as meaningful scaling evidence?

The work should distinguish four claims:

1. **Encoding scalability:** qubits and Hamiltonian terms grow polynomially with `S`, `T` and `H`.
2. **Circuit scalability:** synthesized depth and entangling-gate count remain within a stated growth law on the tested range.
3. **Solution-quality scaling:** the quantum methods' gap or target-success probability deteriorates more slowly than the selected classical heuristics under matched budgets.
4. **Quantum advantage:** end-to-end resource use beats the strongest classical alternative. This is not expected to be demonstrated here.

It is acceptable to establish claims 1-3 partially and present claim 4 only as a conditional future hypothesis. Any extrapolation must include assumptions and must not be plotted as measured data.

Discuss whether the projected depth is compatible with current or fault-tolerant hardware. Do not infer performance merely from qubit count.
